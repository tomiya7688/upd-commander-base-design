# UPD Guideline Levels

この文書は、UPD Commander 設計に含まれる規則・推奨事項・実装上の小技を、強さごとに整理します。

UPD Commander は特定の実装形を強制するフレームワークではなく、UI / Process / Data の責務と通信経路を整理するための設計思想です。

そのため、**性能・メモリ・呼び出しコスト・キャッシュ局所性・配置制約・既存資産との互換性に影響しうる事項は、原則として必須にしません。**

性能が厳しい環境では、推奨構造を簡略化しても、必須条件が守られていれば UPD として成立します。

## 1. 必須 — UPD Core Rules

ここに分類される項目は、UPD として成立するための最低条件です。

### UI / Process / Data の責務を分離する

システムは原則として UI / Process / Data の3つの責務領域へ分離します。

- UI は表示・入力に責任を持つ。
- Process は業務処理・ゲーム処理・計算に責任を持つ。
- Data は保存・取得・永続化に責任を持つ。

物理的に別パッケージ、別クラス、別ファイルへ分けること自体は必須ではありません。性能や環境上の理由がある場合、より平坦な実装でも構いません。

### 層を越える依存経路を制御する

- UI から Data へ直接アクセスしない。
- 別層の Processing を直接呼び出さない。
- Process は UI の表示方式を知らない。
- Data は UI や業務・ゲームロジックを知らない。
- 層固有の型を不必要に境界越しへ漏らさない。

### Commander は処理の交通整理を担当する

Commander は、どの処理をどの順序で呼び出すかを管理します。

Commander 内に複数のルーティング用メソッドを並べる実装は許容されます。重要なのは、Commander 自身が独立した業務処理・ゲーム処理・保存処理を抱え込まないことです。

### Messenger / Communicator は層間通信を担当する

Messenger / Communicator は層を越える通信経路を担当します。

通信メソッドを1つのモジュールやファイルへまとめる実装も許容されます。重要なのは、通信経路の内部へ独立した実処理を混在させないことです。

### 実処理は担当層に置く

計算、変換、描画、保存、取得などの実処理は、それぞれの責務を持つ層へ置きます。

## 2. 推奨 — Recommended Structure

ここに分類される項目は、可読性・保守性・探索性・テスト容易性を高めるために推奨しますが、UPD の成立条件ではありません。

性能、メモリ、呼び出しコスト、ビルド方式、プラットフォーム制約、既存資産等と競合する場合は、採用しない判断ができます。

### 責務単位を小さく保つ

- 1ファイル1責務
- 1モジュール1責務
- クラスを使う場合は1クラス1責務
- 1関数1動作

これらは責務過多を見つけやすくするための推奨事項です。

### Processing を閉じた単位にする

Processing 同士を横方向へ直接結合せず、必要に応じて Commander へ制御を戻す構造を推奨します。

ただし、性能上の理由で呼び出しを統合する必要がある場合まで禁止しません。

### Namespace / package / module とフォルダ構成を合わせる

論理構造と物理構造を一致させ、探索性と責務境界を見やすくするために推奨します。

### Compresser / Container を利用する

引数や返却値が増え、Commander / Messenger が肥大化する場合は、Container 化による通信単位の圧縮を推奨します。

Container 化そのものには生成・コピー・配置等のコストが生じる可能性があるため、一般プロジェクトでは必須としません。

### Application / Sub Application 単位で再帰的に分離する

大規模システムでは、独立した機能境界を Application として扱い、その内部へ再度 UI / Process / Data を適用する構造を推奨します。

小規模システムや性能上単純構造が有利な場合は、不要な階層を増やす必要はありません。

## 3. 小技 — Practical Tips

ここに分類される項目は UPD の成立条件でも推奨構造の必須候補でもなく、実装・レビュー・運用を楽にするための実践テクニックです。

### 処理の意図をコメントで区切る

コードの逐語訳ではなく、「入力検証」「結果計算」「返却」など、処理の目的を示すコメントを使うと読みやすくなります。

### 大きなファイルを責務過多の兆候として見る

UPD を守っている状態では、非常に大きなファイル・型・モジュールは責務過多の可能性があります。

行数やメソッド数は責務そのものではなく、レビュー対象を見つけるヒューリスティックとして利用します。

### 言語に合わせてモジュール表現を変える

UPD はクラスを要求しません。

```text
Go      -> package / file / struct + functions
Python  -> module / class / function group
C++     -> .cpp + .hpp/.h / namespace / class / free functions
C#      -> .cs file / namespace / class
```

言語の自然な表現を優先します。

### 性能が厳しい場合は平坦化する

例えば、次のような実装でも UPD Core Rules を満たせます。

```text
UI
  ├─ Commander methods
  └─ UI processing

Process
  ├─ Commander methods
  └─ Process processing

Data
  ├─ Commander methods
  └─ Data processing

Communicator / Messenger
  └─ communication methods
```

パッケージやクラスを細分化しなくても、責務と通信経路が明確なら UPD として成立します。

### 静的Checkerの警告を設計判断の材料として使う

UPD Checker の Attention / Warning は、機械的に設計を決定するものではありません。

性能測定、プロファイル結果、既存制約等を確認し、必要なら Ignore 理由を残した上で意図的に推奨事項を外せます。

## 4. 判断順序

設計判断では、次の順序を推奨します。

```text
1. UPD Core Rules を守れるか
2. 性能・メモリ・プラットフォーム制約を満たせるか
3. 可能な範囲で Recommended Structure を採用する
4. Practical Tips で可読性・運用性を改善する
```

UPD の目的は、設計のために性能を犠牲にすることではありません。

**最低限の責務分離と依存制御を維持し、その範囲内で実装環境に最適な構造を選択すること**を基本方針とします。
