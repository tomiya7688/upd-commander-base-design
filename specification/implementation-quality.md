# Implementation Quality Requirements

この文書は、UPD Commander 設計を採用する実装が最低限満たすべき品質条件を定義します。

ここで定義する内容は設計上の責務分離そのものではありませんが、規定に準拠した実装として扱うための基礎条件です。

## 1. インデント

- インデントは使用言語・プロジェクトで採用する標準規約に従わなければならない。
- ネスト構造が視覚的に判別できる状態を維持しなければならない。
- 同一ファイル内でインデント方式を混在させてはならない。
- 手動整形より、利用可能であれば formatter の使用を優先する。

## 2. 構文およびビルド可能性

- コードは構文エラーを含んではならない。
- コンパイル言語では通常のビルドを通過しなければならない。
- インタプリタ言語では通常の構文検査・import検査・起動検査を通過しなければならない。
- 未解決参照や通常実行で即時失敗する状態を残してはならない。

## 3. CI適合

- プロジェクトに通常のCIが存在する場合、変更はそのCIを通過しなければならない。
- CIの失敗を無視した状態を標準状態としてはならない。
- CIには少なくとも、プロジェクトで利用している範囲に応じて以下を含めることが望ましい。
  - formatter または format check
  - linter
  - unit test
  - import / compile check
  - build check
  - architecture / dependency check
- CIを通すためだけに、テストや静的解析を無効化してはならない。

## 4. Formatter / Linter

- プロジェクトでformatterが定義されている場合、その結果に従わなければならない。
- プロジェクトでlinterが定義されている場合、通常運用で警告・エラーを放置しない。
- 例外的な無効化が必要な場合は、対象範囲を最小化し理由をコメントまたは設定ファイルに残す。

## 5. テスト

- 既存テストを壊した状態で変更を完了扱いにしてはならない。
- 仕様変更によって既存テストが不適切になった場合は、実装と同時にテスト側も更新する。
- 新規の重要処理には、可能な範囲で対応するテストを追加する。

## 6. 警告の扱い

- ビルド、lint、test、runtimeで継続的に発生する警告は、原則として解消する。
- 意図的に残す警告は、理由と影響範囲を明記する。

## 7. 規定への位置付け

本書の内容は「設計思想として推奨する」項目ではなく、実装を通常品質として受け入れるための適合条件として扱います。

ただし、各プロジェクトの使用言語・ツールチェーン・CI環境によって具体的なコマンドやツールは異なってよいものとします。
