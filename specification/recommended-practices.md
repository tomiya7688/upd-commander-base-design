# Recommended Practices

この文書は UPD Commander 設計における推奨実装規約を定義します。

ここに記載する内容は必須規定ではありませんが、可読性、保守性、疎結合性、テスト容易性を維持するため、特別な理由がない限り従うことを推奨します。

## 1. 1クラス1責務

1つのクラスは、原則として1つの責務のみを持つことを推奨します。

複数の独立した責務を持つクラスは分割してください。

クラス名から説明できない処理が増え始めた場合、そのクラスは責務過多である可能性があります。

特に Commander、Messenger、Processing の責務を同一クラスへ混在させることは避けてください。

## 2. 1関数1動作

1つの関数は、原則として1つの動作のみを担当することを推奨します。

1つの関数内で、取得、検証、計算、保存、描画、通知など複数の独立した動作をまとめて行うことは避けてください。

複数動作が必要な場合は、それぞれを関数へ分割し、Commander または上位処理から順番に呼び出してください。

ただし、1つの責務を完了するために不可分な小さな処理まで過度に分割する必要はありません。

## 3. 処理単位でコメントを付ける

実装には、処理単位が読み取れるコメントを付けることを推奨します。

コメントはコードの逐語的な説明ではなく、処理の目的、区切り、意図を示すために使用してください。

推奨例:

```python
# 入力値を検証する
validate_input(data)

# 戦闘結果を計算する
result = calculate_battle(data)

# 呼び出し元へ返却する
return result
```

非推奨例:

```python
# validate_inputを呼ぶ
validate_input(data)
```

コメントがないと処理の区切りや意図を追いにくいコードは、コメント追加または関数分割を検討してください。

## 4. Commander配下の処理クラスは原則として閉じたクラスにする

Commander から直接呼び出される Processing クラスや処理クラスは、原則として「閉じたクラス」として設計することを推奨します。

ここでいう閉じたクラスとは、原則として次の条件を満たすクラスを指します。

- 親となる Commander から呼び出される。
- 他の Commander 配下の処理クラスから直接呼び出されない。
- 自分から別の Commander 配下の処理クラスを直接呼び出さない。
- 別層の Processing や処理クラスを直接呼び出さない。
- 層間通信が必要な場合は、親 Commander へ制御を返す。
- 別の処理が必要になった場合も、原則として親 Commander に判断を戻す。

基本形:

```text
Commander
  ├─ Processing A
  ├─ Processing B
  └─ Processing C
```

推奨される呼び出し:

```text
Commander
  ↓
Processing A
  ↓
Commanderへ結果を返す
  ↓
Commander
  ↓
Processing B
```

避けるべき呼び出し:

```text
Commander
  ↓
Processing A
  ↓
Processing B
  ↓
別Commander配下のProcessing C
```

この規則の目的は、Processing 同士が横方向に結合し、Commander を経由しない隠れた実行経路が増えることを防ぐことです。

## 5. 閉じたクラスの例外

次のような場合は、閉じたクラスの内部から補助処理を呼び出しても構いません。

- 同一責務を補助する純粋関数
- 同一クラス内部の private 相当処理
- 値オブジェクトやデータ構造
- 副作用を持たない共通変換処理
- プロジェクト内で明示的に共通部品として定義されたユーティリティ

ただし、その補助処理が独立した業務判断、ゲームロジック、保存、UI更新、別層アクセスを始める場合は、親 Commander を経由する構造へ戻すことを推奨します。

## 6. 推奨するレビュー観点

コードレビューでは、少なくとも次を確認することを推奨します。

- クラスに複数責務が混在していないか。
- 関数が複数の独立動作を抱えていないか。
- 処理の区切りと意図が読み取れるか。
- Processing 同士が横方向へ直接結合していないか。
- Commander を迂回する呼び出し経路が増えていないか。
- コメントがコードの言い換えではなく、意図を説明しているか。

## 要約

UPD Commander 設計では、Commander を処理の交通整理役として保ち、その配下の処理クラスを可能な限り閉じた単位にします。

推奨する基本形は次の通りです。

```text
1クラス = 1責務
1関数   = 1動作
処理単位 = 意図を示すコメント
Processing = 原則として親Commander配下に閉じる
```
