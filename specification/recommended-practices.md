# Recommended Practices

この文書は UPD Commander 設計における推奨実装規約を定義します。

ここに記載する内容は必須規定ではありませんが、可読性、保守性、疎結合性、テスト容易性を維持するため、特別な理由がない限り従うことを推奨します。

## 1. 1ファイル1責務

1つのファイルは、原則として1つの責務のみを持つことを推奨します。

多くの言語では、ファイルまたはモジュールが名前空間、可視性、公開範囲、依存境界などのアクセス制御単位として機能します。

そのため UPD Commander 設計では、ファイル境界を基本的な責務境界として扱います。

複数の独立した責務を持つファイルは分割してください。

ファイル名から説明できない処理が増え始めた場合、そのファイルは責務過多である可能性があります。

特に Commander、Messenger、Processing の責務を同一ファイルへ混在させることは避けてください。

## 2. 1モジュール1責務

1つのモジュールは、原則として1つの責務のみを持つことを推奨します。

ここでいうモジュールとは、特定の責務を持つ独立した実装単位を指します。

モジュールの具体的な表現方法は使用言語に依存します。

代表例:

```text
Go      -> package / file / struct + functions
Python  -> .py module / class / function group
C++     -> .cpp + .hpp/.h / namespace / class
C#      -> .cs file / namespace / class
C       -> .c + .h
Rust    -> module / struct + impl
関数型言語 -> module / function group
```

現在 UPD Commander 設計を適用する主要な実装言語では、次のように考えます。

### Go

Go では package が比較的大きな公開・依存境界となり、その内部を複数ファイルへ分割できます。

UPD Commander 設計では、package 内でも責務ごとにファイルを分割し、1ファイルへ独立した複数責務を詰め込まないことを推奨します。

```text
process/
├─ commander.go
├─ messenger.go
├─ battle_processing.go
└─ movement_processing.go
```

必要に応じて `struct + method` を使用しても構いませんが、struct を使うこと自体は必須ではありません。状態を持たない処理は関数群として実装しても構いません。

### Python

Python では `.py` ファイル自体をモジュールとして扱えます。

そのため、UPD Commander 設計では1つの `.py` ファイルを1つの責務単位として扱う構造が自然です。

```text
process/
├─ commander.py
├─ messenger.py
├─ battle_processing.py
└─ movement_processing.py
```

クラスが必要な場合は使用して構いませんが、単純な処理をクラス化する必要はありません。関数のみで責務を表現できる場合は、モジュール + 関数でも同じ設計を実現できます。

### C++

C++ では `.cpp` と `.hpp` / `.h` の組を1つの実装モジュールとして扱うことができます。

```text
process/
├─ Commander.cpp
├─ Commander.hpp
├─ Messenger.cpp
├─ Messenger.hpp
├─ BattleProcessing.cpp
├─ BattleProcessing.hpp
├─ MovementProcessing.cpp
└─ MovementProcessing.hpp
```

クラスを利用する場合は、原則として1クラスを1責務へ対応させ、ファイル境界と責務境界が可能な限り一致する構造を推奨します。

ただし、UPD Commander 設計上のモジュールはクラスそのものではありません。namespace、自由関数、内部リンケージ等を使った非OOP実装でも同じ設計を実現できます。

### C#

C# ではクラスを主要な実装単位として使用することが一般的ですが、UPD Commander 設計ではクラスより先にファイル・モジュールの責務を定義します。

```text
Process/
├─ ProcessCommander.cs
├─ ProcessMessenger.cs
├─ BattleProcessing.cs
└─ MovementProcessing.cs
```

原則として、1つの主要クラスを1ファイルへ配置し、そのクラスをファイルの責務と対応させる構造を推奨します。

ただし、補助型、record、enum、内部型などを同一ファイルへ置くことまで禁止するものではありません。同一責務の範囲内であることを優先します。

## 3. 1関数1動作

1つの関数は、原則として1つの動作のみを担当することを推奨します。

1つの関数内で、取得、検証、計算、保存、描画、通知など複数の独立した動作をまとめて行うことは避けてください。

複数動作が必要な場合は、それぞれを関数へ分割し、Commander または上位処理から順番に呼び出してください。

ただし、1つの責務を完了するために不可分な小さな処理まで過度に分割する必要はありません。

## 4. 処理単位でコメントを付ける

実装には、処理単位が読み取れるコメントを付けることを推奨します。

コメントはコードの逐語的な説明ではなく、処理の目的、区切り、意図を示すために使用してください。

推奨例:

```python
# 入力値を検証する
validate_input(data)

# 戦闘結果を計算する
result = calculate_battle(data)

# 呼び出し元へ返却する
return result
```

非推奨例:

```python
# validate_inputを呼ぶ
validate_input(data)
```

コメントがないと処理の区切りや意図を追いにくいコードは、コメント追加または関数分割を検討してください。

## 5. Commander配下の処理モジュールは原則として閉じたモジュールにする

Commander から直接呼び出される Processing モジュールや処理モジュールは、原則として「閉じたモジュール」として設計することを推奨します。

ここでいう閉じたモジュールとは、原則として次の条件を満たす処理単位を指します。

- 親となる Commander から呼び出される。
- 他の Commander 配下の処理モジュールから直接呼び出されない。
- 自分から別の Commander 配下の処理モジュールを直接呼び出さない。
- 別層の Processing や処理モジュールを直接呼び出さない。
- 層間通信が必要な場合は、親 Commander へ制御を返す。
- 別の処理が必要になった場合も、原則として親 Commander に判断を戻す。

基本形:

```text
Commander
  ├─ Processing A
  ├─ Processing B
  └─ Processing C
```

推奨される呼び出し:

```text
Commander
  ↓
Processing A
  ↓
Commanderへ結果を返す
  ↓
Commander
  ↓
Processing B
```

避けるべき呼び出し:

```text
Commander
  ↓
Processing A
  ↓
Processing B
  ↓
別Commander配下のProcessing C
```

この規則の目的は、Processing 同士が横方向に結合し、Commander を経由しない隠れた実行経路が増えることを防ぐことです。

## 6. 閉じたモジュールの例外

次のような場合は、閉じたモジュールの内部から補助処理を呼び出しても構いません。

- 同一責務を補助する純粋関数
- 同一モジュール内部の private 相当処理
- 値オブジェクトやデータ構造
- 副作用を持たない共通変換処理
- プロジェクト内で明示的に共通部品として定義されたユーティリティ

ただし、その補助処理が独立した業務判断、ゲームロジック、保存、UI更新、別層アクセスを始める場合は、親 Commander を経由する構造へ戻すことを推奨します。

## 7. OOP言語におけるクラスの位置付け

UPD Commander 設計はオブジェクト指向を前提としません。

クラスを持つ言語では、クラスをモジュールの具体的な実装方法として使用して構いません。

ただし、設計上の優先順位は次の通りです。

```text
ファイル / モジュール境界
  ↓
責務境界・依存境界・アクセス制御境界
  ↓
必要に応じてクラス等の内部構造
```

つまり、クラス境界よりもファイルおよびモジュール境界を先に設計します。

1ファイルに複数クラスを配置すること自体は禁止しませんが、それによって複数の独立責務が1ファイルへ混在する場合は分割を推奨します。

## 8. 推奨するレビュー観点

コードレビューでは、少なくとも次を確認することを推奨します。

- 1ファイルに複数の独立責務が混在していないか。
- 1モジュールに複数の独立責務が混在していないか。
- 関数が複数の独立動作を抱えていないか。
- 処理の区切りと意図が読み取れるか。
- Processing 同士が横方向へ直接結合していないか。
- Commander を迂回する呼び出し経路が増えていないか。
- クラスを使用することでファイルまたはモジュール境界が曖昧になっていないか。
- コメントがコードの言い換えではなく、意図を説明しているか。

## 要約

UPD Commander 設計では、Commander を処理の交通整理役として保ち、その配下の処理モジュールを可能な限り閉じた単位にします。

推奨する基本形は次の通りです。

```text
1ファイル   = 1責務
1モジュール = 1責務
1関数       = 1動作
処理単位     = 意図を示すコメント
Processing  = 原則として親Commander配下に閉じる
Class       = OOP言語におけるモジュール実装例の1つ
```
