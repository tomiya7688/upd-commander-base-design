# 日本語ドキュメント執筆ガイド

このガイドは、このリポジトリの `README`、`docs/`、`specification/`、Checker README を日本語で書くときの基準です。内容を正確にするだけでなく、UPDを初めて読む人が、別の文書を先に読まなくても要点をつかめることを目指します。

## まず読者と目的を決める

書き始める前に、次の2点を決めます。

- 誰が読む文書か。例: UPDを初めて導入する人、設計判断をする人、Checkerを実装する人。
- 読み終えた人が何を理解し、何をできるようになるか。

冒頭の数段落には、対象読者、文書の目的、この文書で分かることを置きます。前提となる用語や別文書がある場合は、先に短く説明するか、読む理由が分かるリンクを示します。

## 読み進めやすい順序にする

基本は「結論・全体像 → 具体例 → 理由 → 条件や例外 → 詳細仕様」です。技術文書では概念を先に説明し、その後に判定式、JSON schema、ASTなどの実装用語を示します。

1段落では1つの論点を説明します。主語や対象を省略して意味が曖昧になる場合は、何が何をするのかを書き直します。「これ」「それ」「対象」などを使うときは、指すものが直前の文から特定できることを確認します。

## 用語を説明してから使う

専門用語や英語の用語は、初出時に短い日本語の説明を添えます。説明だけで伝わりにくいときは、直後に具体例を示します。英語を続けて並べるだけで説明したことにしません。

例:

- 説明不足: `baseline fingerprintを比較します。`
- 改善例: `baselineは、以前に見つかった問題を記録した一覧です。fingerprintは、行番号が変わっても同じ問題を識別するためのIDです。`

文書内で同じ概念に複数の呼び名を使わないようにします。既定の用語は該当する仕様書や用語集に合わせ、名称を変更する場合は関連文書も確認します。

## 規則の強さを正しく伝える

文書を書く前に、その説明が必須規則、推奨事項、小技のどれかを決めます。UPDでの分類の正本は [Guideline Levels](../specification/guideline-levels.md) です。必須でない設計判断を「必ず」「禁止」と書いてはいけません。反対に、必須規則を単なる推奨のように弱めてはいけません。

- **必須規則**: 守らなければ設計要件を満たさない条件です。正本となる仕様と、適用範囲を示します。
- **推奨事項**: 原則として採用する価値がありますが、性能、プラットフォーム、既存構成などの理由で採用しない判断もできます。理由と例外条件を示します。
- **小技**: 作業や理解を助ける方法です。必須条件のように扱いません。

Checker severityとの対応は [Checker Severity Boundary](../specification/checker-severity.md) を正本とします。規則の強さとChecker severityの対応関係は仕様で定義されます。別の用語体系を説明なしに同じ意味だとみなしたり、Checker severityの名称だけから規則の強さを推測したりしてはいけません。

例外を認める規則では、対象範囲と判断理由を明記します。例外を使うときは、理由、影響範囲、代替案、将来取り除けるかを記録できる形にします。

## 一般アプリとゲームの両方で例を考える

例がゲーム開発だけに偏らないようにします。可能なら、同じ考え方を一般アプリとゲームの例で示します。

| 考え方 | 一般アプリの例 | ゲームの例 |
| --- | --- | --- |
| UIからDataへ直接依存しない | 画面がDB repositoryを直接呼ばず、Process経由で検索する | 画面がセーブデータを直接更新せず、Process経由で保存する |
| 実処理をCommanderに集めない | Commanderは入力検証や検索処理を呼び分け、計算はProcessingへ置く | Commanderはターン処理を呼び分け、ダメージ計算はProcessingへ置く |

例は規則の説明を助けるものです。例の実装名やフォルダ名を、明示しないまま必須ルールへ変えてはいけません。

## 概要文書と技術仕様を分ける

`docs/` は概念や判断の理由を説明し、`specification/` は実装で一致させる規則や契約を定義します。概要文書では、読者が判断に使える例を先に置きます。技術仕様では、その後に境界値、schema、fixture、エラー条件などを正確に記載します。

規則を説明するときは、必要に応じて次の順でまとめます。

1. 何を求める規則か
2. なぜ必要か
3. 正しい例と避ける例
4. 適用範囲と例外
5. Checkerで確認する場合の判定方法

## 文書を変更したときの確認

文書を更新したら、対象読者が冒頭から読み進められるか、リンク先が存在するか、同じ規則を扱う正本・翻訳・READMEと矛盾しないかを確認します。規則の強さや用語を変更した場合は、関連するChecker・fixture・設定例も調べます。
